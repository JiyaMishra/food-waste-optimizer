4. Step-by-step implementation
Step 1 — Set up the frontend
Create a React application with Vite and TypeScript if the shared project uses TypeScript.
Install/configure Tailwind CSS and Plotly (or the agreed chart library).
Create src/api/, src/components/, src/pages/, src/charts/ and src/types/.
Set VITE_API_BASE_URL through environment configuration; never put backend secrets in Vite variables.
Create a reusable API client with request timeouts, response parsing and consistent error handling.
Done when: The frontend starts locally and can successfully call the backend health endpoint.
Step 2 — Define UI data types and reusable components
Create types/interfaces for meal, dish, forecast, uncertainty bounds, rush interval, diagnosis cause, batch plan, simulation state, evaluation metrics and agent trace.
Build reusable page layout, navigation, status badges, synthetic-data banner, chart wrappers, loading indicators, empty states and error messages.
Use explicit units and labels; distinguish portions from kilograms.
Show model version, scenario ID, forecast cutoff and uncertainty where relevant.
Avoid hardcoded demo values in production UI components; use fixture data only for isolated UI tests.
Done when: All pages share consistent components and typed API responses.
Step 3 — Build the Overview page
Display the selected synthetic scenario, date and meal type.
Show expected attendance, forecast demand, waste risk, shortage risk, latest run status and recent interventions using API data.
Provide controls to choose scenario/date/meal and start a run using the backend endpoint.
Keep a persistent SYNTHETIC DEMO DATA banner anywhere generated records or simulated results are shown.
Show a clear empty state before data has been generated.
Done when: The overview can start a real backend run and displays values returned by the API.
Step 4 — Build Meal Planner and Rush Timeline
Meal Planner: show menu items, total and dish-level forecasts, uncertainty ranges, initial/reserve quantities, capacity, lead time and rationale.
Allow only the configuration changes supported by backend endpoints; validate before sending requests.
Rush Timeline: chart predicted arrivals by interval and label low/normal/high rush using backend results.
Label axes, units and the synthetic status. Provide a way to inspect the context/rationale for an interval.
Display API errors when no model artifact, scenario or forecast is available.
Done when: Forecast and plan screens are driven by API results and clearly explain quantities and uncertainty.
Step 5 — Build Context & Availability and Waste Diagnosis
Context & Availability: show synthetic occupancy, class/lab/exam overlap, event effects, weather context and available-population estimates.
Waste Diagnosis: show ranked possible causes, evidence, uncertainty/confidence caveats and before/after comparisons when supported.
Clearly separate estimated pre-meal risk from retrospective post-simulation diagnosis.
Never display a cause as proven if the backend only reports an association or uncertain candidate.
Show missing-data warnings returned by the backend.
Done when: Context and diagnosis pages expose evidence and limitations without inventing explanations.
Step 6 — Build Kitchen Live Simulation
Show current interval, arrivals so far, remaining stock, batch status and projected end-of-service stock.
Provide controls to start, advance one interval, finish the meal and view events, mapped to the backend simulation endpoints.
Disable invalid controls based on run status and handle API rejection gracefully.
Display replenishment/hold actions with the trigger reason, timestamp and approval/simulation status.
At meal close, show prepared, served, consumed, untouched leftover, plate waste and shortage separately.
Do not label a recommendation as executed unless the backend confirms the simulated action.
Done when: The user can run a complete simulation through the UI and see the persisted final outcome.
Step 7 — Build Menu Analytics, Evaluation, Agent Trace and Settings
Menu Analytics: compare dish acceptance, repetition, demand and waste rates across comparable synthetic contexts.
Evaluation: compare baseline and context-aware forecasting metrics and fixed-batch versus context-aware policy outcomes separately.
Agent Trace: display each stage, input summary, tool/function calls, output, duration, status and errors.
Settings/Data: show generation seed, dataset/scenario versions, model version and available demo controls.
Add CSV/JSON export using the backend's export route or a documented supported client-side export.
Explain metric denominators and show a suitable message when R² or percentage reduction is undefined.
Done when: Every page reads its values from backend data and handles missing/empty results.
Step 8 — Integrate and test the full workflow
Run the frontend and backend together using documented local commands.
Test: generate synthetic data → choose scenario → calculate context/availability → forecast → plan → start simulation → advance intervals → finish → view evaluation → inspect agent trace → export.
Test loading, slow responses, timeouts, invalid inputs, missing data, server errors and stale run IDs.
Check chart axes, legends, units, responsive layout, readable text and clear status messages.
Confirm the synthetic-data banner is visible wherever generated data/results appear.
Use automated frontend tests for key components and a documented manual end-to-end checklist.
Done when: A teammate can complete the full demo path without manually editing the database or source code.
Step 9 — Prepare Docker configuration
Create a frontend Dockerfile and backend Dockerfile if they are not already supplied.
Create or complete Docker Compose for frontend, backend and PostgreSQL, including database health checks and service dependencies.
Use environment variables and an .env.example with placeholders; do not commit .env files, passwords, API keys or tokens.
Ensure migrations run as a controlled startup/release step and demo data is generated through an explicit command/action rather than on every app start.
Check that model artifacts and database data persist as required and are not lost when containers restart.
Test a clean build from the repository instructions.
Done when: Docker Compose can start the full local application from a clean setup and data/model persistence behaves as documented.
Step 10 — Deploy the application
Choose one frontend host, one backend/container host and a managed PostgreSQL service or the agreed hosting architecture.
Set production environment variables, allowed CORS origins and database credentials securely.
Use HTTPS, least-privilege database credentials, restricted CORS and appropriate request timeouts/rate limits.
Configure health/readiness checks and verify database connectivity and model-file loading.
Do not expose backend secrets in Vite environment variables or frontend bundles.
Record the deployed URL, commit hash, model version and database migration version.
Done when: The deployed application is reachable and health/readiness checks pass.
Step 11 — Run deployed smoke tests
Against the deployed URL, test health, data generation, forecast, planning, simulation start/step/finish, evaluation and export.
Verify all values are derived from the deployed backend/database and that the synthetic banner is present.
Check logs for failures, CORS errors, missing model artifacts, migration problems and unhandled exceptions.
Verify secrets are not exposed and refresh/restart behavior does not unexpectedly erase required records.
Record each test as pass/fail with evidence and list any manual step still required.
Done when: The complete workflow works on the deployed environment, with documented results and known limitations.
Step 12 — Prepare final documentation and demonstration
Create/update README with architecture, setup, environment variables, migrations, data generation, tests and deployment instructions.
Include architecture diagram, data flow, screenshots, sample evaluation report, limitations and source attribution.
Prepare a 5–7 minute demo: open overview and synthetic banner; select early-class rush or exam morning; inspect context and forecast; review batch plan; run simulation; inspect diagnosis, outcomes, evaluation and agent trace.
Make sure each team member can explain their own implementation and the end-to-end pipeline.
Do not claim public hosting proves real-world waste reduction; it proves the hosted prototype workflow works.
Done when: A new evaluator can access the application and follow the demo script without special undocumented steps.

8. Common mistakes to avoid
Hardcoding forecast values, waste-reduction percentages or chart data.
Making UI controls that do not call a working backend action.
Silently assuming a successful action before the API confirms it.
Putting database passwords or model-provider keys in VITE_* variables.
Generating a new dataset on every app restart and making results irreproducible.
Showing only a success message while ignoring backend validation errors.
Using vague charts without units or denominators.
Claiming the prototype is connected to live VIT attendance, weather or kitchen systems when it is not.
Calling synthetic results proof of actual food-waste reduction.
